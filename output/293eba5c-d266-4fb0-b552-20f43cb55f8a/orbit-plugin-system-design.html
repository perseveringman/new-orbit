ORBIT PLUGIN SYSTEM · 协议代号 orbit.app/1

Orbit 插件体系设计方案

让用户在 Orbit 里搭出一个「一等公民」式的扩展：拥有自己的页面布局、文件优先的数据结构、以及暴露给 Agent 的 tools，并与 Orbit 的 Vault / Inbox / Activity / Approval 等核心能力无缝运转起来。本方案基于对 Orbit 现有 Electron 三进程架构与 Shadow shadow.app/1 协议的对照分析得出。

01设计目标与 Shadow 对照

你要的能力可以拆成四条硬指标，每条都需要对接 Orbit 的一个既有子系统：

诉求含义对接 Orbit 子系统
能用 Orbit 的能力插件可读写 vault、提任务、发 Inbox、查搜索/语义索引CliHandlerRegistry + 新增 OrbitCapabilityGateway
有自己的页面布局像 Kanban/Feed 一样在主工作区有独立 View + 右侧栏 profileVaultViewKind + SURFACE_PROFILES + 新增 PluginViewHost
文件优先的数据结构插件数据是 Markdown/JSON 落在 vault 里，Git 可追踪Vault .orbit/ 布局 + RefmapStore 约定
暴露 tools 给 Orbit插件命令自动注册进 OrbitToolRegistry，Agent 可调AgentToolDef + OrbitToolExecutor
与 Shadow 的本质差异：Shadow 的 shadow.app/1 插件是跨进程的独立 HTTP 服务（manifest URL + OAuth 内省 + iframe）。Orbit 是单机 Electron 本地优先应用，没有多租户服务端，因此不应照搬 HTTP/OAuth 那套。Orbit 插件应是进程内沙箱模块 + 文件契约。但 Shadow 的三个抽象值得继承：(1) Manifest 声明能力、(2) Command = JSON Schema 化的 RPC、(3) iframe + Bridge 做 UI 隔离。

从 Shadow 借鉴 → 映射到 Orbit

Shadow shadow.app/1Orbit orbit.app/1 对应物
/.well-known/shadow-app.json Manifestplugin.json（本地包内 manifest，无需 URL）
OAuth2 Bearer + Token Introspection主进程内 CapabilityGrant（能力授予表，无网络）
commands[] + inputSchemacommands[] → 直接生成 AgentToolDef（已有 JSON Schema 机制）
iframe.entry + allowedOrigins + postMessage Bridge<webview> / iframe + OrbitBridge postMessage
shadow.outbox.inboxTasks（回写 Buddy Inbox）插件命令返回 orbit.outbox → 写 Orbit Inbox / Approval
access.defaultPermissions / approvalMode复用 Orbit 既有 AuthorityPermission / AuthorityRiskLevel

02Orbit 现有架构的 5 个挂载点

插件体系不需要新造轮子——Orbit 已经把所有扩展点都铺好了，插件系统本质是把这 5 个点「编织」起来：

① IPC 契约 (src/shared/ipc.ts)

main/preload/renderer 单一契约。新增 plugin namespace：plugin:list / install / activate / invoke / viewState。preload 经 contextBridge 暴露 window.orbit.plugin.*。

② Agent Tool 注册表 (main/agent-tools/registry.ts)

OrbitToolRegistry.register(AgentToolDef) 已支持运行时注册 + listForScope 过滤。插件命令直接转成 AgentToolDef 注册进去，Agent 立刻可见。

③ CLI Handler 注册表 (main/cli_server/registry.ts)

CliHandlerRegistry.register(method, handler) 是 tool 的真正执行体（AgentToolDef.cliMethod 指向它）。插件命令注册成 plugin.<key>.<cmd> 形式的 handler。

④ View 导航 (vaultRightSidebarModel.ts)

VaultViewKind 枚举 + SURFACE_PROFILES 决定主工作区渲染什么 + 右侧栏布局。插件 View 动态扩展这两张表。

⑤ 文件优先存储 (main/*/store.ts 范式)

如 ResourceStore：构造接 vaultPath，所有数据是 vault 下的 Markdown + frontmatter + 一个 _index.json，Watcher 增量刷新。插件数据沿用同一范式。

⊕ 新增：Plugin Host (粘合层)

唯一需要新写的核心模块。负责扫描插件包 → 校验 manifest → 注册 tools/handlers/views → 创建能力网关 → 管理生命周期。是上述 5 点的编排者。

关键发现：Orbit 的 tool 执行链已经是「AgentToolDef.cliMethod → CliHandlerRegistry.handle() → 返回 JSON」的解耦设计（见 executor.ts）。这意味着插件命令天然可以复用整条执行、超时、Activity 留痕、journal 管线，无需改动 executor。这是把插件做成「一等 tool」最大的红利。

03插件形态选型（关键决策）

有三种可选形态，建议分层采用 B（默认）+ C（高级）：

形态说明隔离/安全建议
A. 进程内 JS 模块插件是一个被 main 动态 import() 的 TS/JS 包，直接拿到能力网关对象弱（同进程，能力靠网关收口）官方/可信插件
B. UI=iframe + 逻辑=声明式 manifest页面跑在沙箱 <iframe sandbox>，命令是「声明 cliMethod 映射 + JSON Schema」，不跑任意 JS 后端强（UI 沙箱 + 无后端代码）默认形态 ✓
C. utilityProcess 沙箱插件后端逻辑跑在 Electron utilityProcess 子进程，经 MessagePort 与 main 通信（类似 Shadow 跨进程）最强（独立进程，可限权）需要自定义后端逻辑时

形态 B 覆盖你描述的 80% 场景（"用户自己在 orbit 里做一个页面，这个页面能和 orbit 运转起来"）：页面是 iframe，数据是 vault 文件，命令是把已有 Orbit 能力组合 / 编排。形态 C 留给需要跑爬虫、解析、长任务等自定义后端的高级插件。

iframe View⇄ postMessage OrbitBridge→ Plugin Host→ CapabilityGateway→ CliHandlerRegistry / Stores

04插件包结构与 Manifest

插件以「包目录」分发，可放在 vault 内（用户私有、Git 同步）或全局插件目录（跨 vault 共享）：

<vault>/.orbit/plugins/<plugin-key>/      # 或 ~/Library/Application Support/Orbit/plugins/
├── plugin.json                # ① Manifest（声明能力，下文详述）
├── ui/                        # ② 前端构建产物（iframe 入口）
│   ├── index.html
│   └── assets/app.js
├── commands/                  # ③ (形态C才有) 后端命令实现
│   └── index.ts
├── schema/                    # ④ 命令 inputSchema（也可内联进 manifest）
└── icon.svg

plugin.json — 借鉴 shadow-app.json 但本地化

{
  "schemaVersion": "orbit.app/1",
  "key": "habit-tracker",
  "name": "Habit Tracker",
  "version": "1.0.0",
  "kind": "iframe",                          // iframe | utilityProcess | module
  "icon": "icon.svg",

  "view": {                                   // ⇒ 注册成一等 VaultViewKind
    "entry": "ui/index.html",
    "title": "习惯",
    "navGroup": "capture",                    // 决定它出现在侧边导航哪一组
    "sidebar": {                              // ⇒ 注入 SURFACE_PROFILES
      "intents": [{ "id": "overview", "panels": ["inspector"] }]
    }
  },

  "data": {                                   // ⇒ 文件优先数据契约
    "root": "05_Plugins/habit-tracker",       // vault 相对根目录
    "indexFile": "_index.json",
    "entryType": "habit"                      // frontmatter type 命名空间
  },

  "capabilities": [                           // ⇒ 申请的 Orbit 能力（审批据此）
    "vault.read", "vault.writeOwnData",
    "task.propose", "inbox.emit", "search.query"
  ],

  "commands": [                               // ⇒ 每条自动注册成 AgentToolDef
    {
      "name": "habit_log",                    // Agent 看到的 tool 名
      "title": "记录一次习惯打卡",
      "description": "When the user completes a habit, log today's check-in.",
      "handler": "habit.log",                 // 形态B: 映射到内置编排; 形态C: 插件后端方法
      "risk": "L1_reversible",
      "permissions": ["write_vault_direct"],
      "inputSchema": {
        "type": "object", "required": ["habitId"],
        "properties": {
          "habitId": { "type": "string" },
          "note": { "type": "string" }
        }, "additionalProperties": false
      },
      "outbox": { "inbox": false, "activity": "plugin.habit_logged" }
    }
  ],

  "events": ["habit.updated"]                 // 插件可广播的事件（renderer 订阅）
}

注意：commands[].inputSchema 与 risk/permissions 与 Orbit 现有 AgentToolDef 字段一一对应，Plugin Host 几乎是直译。这正是复用 OPENCLAW / Authority 体系的好处。

05文件优先的数据结构

遵循 Orbit 既有的 ResourceStore / SpaceLayout 范式，插件数据 = vault 下的目录，Markdown + frontmatter 为真相、_index.json 为加速缓存，由 Watcher 增量维护、Git 追踪。新增一个 PARA 同级目录 05_Plugins/：

<vault>/05_Plugins/habit-tracker/
├── _index.json                # { version, entries:[{uid,relPath,hash}], updatedAt }
├── _config.md                 # 插件用户配置（frontmatter）
├── morning-run.md             # 一条数据 = 一个 Markdown
│   #   ---
│   #   uid: habit-3f2a            ← 接入 RefmapStore（不可变）
│   #   type: habit                ← manifest.data.entryType
│   #   plugin: habit-tracker      ← 归属插件（隔离/查询用）
│   #   created: 2026-06-01T...
│   #   ---
│   #   # 晨跑
└── _outputs/                   # 复用 SPACE_OUTPUTS_DIR 语义（持久产物）

真相在文件

每条记录是独立 .md，uid/type/created 不可变（沿用 Orbit 迁移规则），用户可用任何编辑器改、Git diff 可读。

索引可重建

_index.json 只是缓存。删了能从 Markdown 全量重扫恢复。接入 VaultWatcher 的 fs:event 增量更新。

RefmapStore 接入

插件数据的 uid → relPath 写入全局 refmap，于是 [[wikilink]]、反向链接、搜索、语义索引自动覆盖插件数据。

Plugin Host 提供一个泛型 PluginDataStore(vaultPath, manifest.data)，封装 list / get / create / update / archive，直接抄 ResourceStore 的 frontmatter 读写 + index 维护逻辑。插件作者不用碰 fs，只声明 entryType 和 schema。

06页面布局：把插件注册成一等 View

Orbit 的 View 系统是静态枚举 + profile 表（VaultViewKind 联合类型 + SURFACE_PROFILES 字典）。要让插件页面成为一等公民，需要把这两处从「编译期静态」改为「运行期可扩展」。改动范围很小：

① 扩展 VaultViewKind / SidebarSurfaceId

新增一个通配成员 'plugin'，并让 view 携带 pluginKey（类比现有 project view 携带 projectUid）：

// vaultRightSidebarModel.ts
export type VaultViewKind = /* ...既有... */ | 'plugin';

export function resolveSidebarSurface(view, projectMode) {
  if (view.kind === 'plugin') return `plugin.${view.pluginKey}`;   // 动态 surface
  /* ...既有逻辑... */
}

// SURFACE_PROFILES 从 const 字典 → 可写 Map，Plugin Host 在 activate 时注入：
pluginHost.on('activate', (m) =>
  registerSurfaceProfile(`plugin.${m.key}`, m.view.sidebar ?? DEFAULT_PLUGIN_PROFILE));

② 渲染层：PluginViewHost 组件

在 VaultView 的 view 分发 switch 里加一个分支：当 view.kind === 'plugin' 时渲染 <PluginViewHost pluginKey>，它内部就是一个受控 iframe + Bridge：

function PluginViewHost({ pluginKey }) {
  const src = useOrbit().plugin.viewUrl(pluginKey);   // orbit-plugin://<key>/ui/index.html
  return <iframe
    sandbox="allow-scripts"                            // 关键：禁 same-origin / 禁 top-navigation
    src={src}
    onLoad={() => bridge.attach(pluginKey)} />;
}
iframe 用自定义 protocol orbit-plugin://（在 main 用 protocol.registerFileProtocol 注册，作用域锁死到该插件 ui/ 目录），配合 sandbox="allow-scripts"，让插件 UI 拿不到 Node、拿不到 window.orbit、跨域隔离。一切能力只能经 Bridge 的 postMessage 走。等价于 Shadow 的 iframe + allowedOrigins。

③ 导航入口

Sidebar 的导航组（navGroup）渲染时合并「内置 view 列表 + 已激活插件列表」。用户点插件项 → workspace.openView({ kind:'plugin', pluginKey })。整套右侧栏 inspector / ask-anywhere 因为走 surface profile，自动对插件页面生效。

07暴露 Tools 给 Orbit Agent

这是「插件能和 Orbit 运转起来」的核心。Plugin Host 在激活插件时，把每条 manifest.commands[] 翻译成 AgentToolDef 注册进 OrbitToolRegistry，并把执行体注册进 CliHandlerRegistry：

// Plugin Host 激活流程（伪代码）
for (const cmd of manifest.commands) {
  const cliMethod = `plugin.${manifest.key}.${cmd.name}`;

  // 1) 注册执行体到 CLI 注册表（tool/cli 共用一条执行链）
  cliRegistry.register(cliMethod, async (params) =>
    pluginRuntime.invoke(manifest.key, cmd.handler, params, capabilityGateway));

  // 2) 翻译成 AgentToolDef → Agent 立刻可见、可调
  toolRegistry.register({
    name: cmd.name,                       // 如 habit_log
    description: cmd.description,
    inputSchema: cmd.inputSchema,
    cliMethod,                            // ← 指向上面的 handler
    destructive: cmd.risk !== 'L0_observe',
    family: 'plugin',
    risk: cmd.risk,
    permissions: cmd.permissions,
    source: 'orbit',
    activity: { successAction: cmd.outbox?.activity ?? 'plugin.tool_invoked' },
    scopes: cmd.scopes                    // 可限定只在某些会话 scope 暴露
  });
}
零改动复用：因为走的是既有 OrbitToolExecutor 链路，插件 tool 自动获得：30s 超时保护、结果截断、runtime.tool_result 事件、destructive 工具的 journal + Activity Log 留痕、scope 过滤。Agent 在对话里说"帮我记录晨跑打卡"就能调到 habit_log。

同时，这些 tool 也自动出现在 orbit CLI（agent-facing 入口）和 ToolRegistryView 工具注册页面里——和 Orbit 内置工具完全平权。

08能力网关：插件如何反过来用 Orbit 的能力

插件不仅要暴露 tool，还要消费 Orbit 能力（写 vault、提任务、发 Inbox、查搜索）。这通过 CapabilityGateway 收口——它是 Shadow 「OAuth scope」在本地的等价物，但是一张内存授权表，无网络。

class CapabilityGateway {
  constructor(private pluginKey, private granted: Set<Capability>,
              private cli: CliHandlerRegistry, private dataStore) {}

  // 每个方法先查 granted，未授权直接抛 capability_denied
  async vaultRead(relPath)  { this.assert('vault.read');
    return this.cli.handle({ method:'cat', params:{ target: this.scope(relPath) }}); }

  async writeOwnData(entry) { this.assert('vault.writeOwnData');
    return this.dataStore.create(entry); }            // 只能写自己的 data.root

  async proposeTask(input)  { this.assert('task.propose');
    return this.cli.handle({ method:'task.propose', params: input }); }  // → 进 Inbox 审批

  async emitInbox(item)     { this.assert('inbox.emit');  /* → Inbox hub */ }
  async search(q)           { this.assert('search.query'); /* MiniSearch */ }
  async semantic(q)         { this.assert('semantic.query'); /* 向量检索 */ }
}

能力清单（映射到 Orbit 子系统）

Capability底层风险
vault.readCLI cat/search（限插件 data.root + 显式授权外部路径走 ExternalPathApproval）读
vault.writeOwnDataPluginDataStore（仅限 05_Plugins/<key>/）受限写
task.proposetask.propose → Approval → Inbox（agent 不能直接建 task，符合 propose-approve）提议
inbox.emitInbox hub 写入 item（capture 类）写
search.query / semantic.querySearchIndex / 向量库（只读）读
vault.writeAny跨目录写——默认禁用，需 every_time 审批高危
Outbox 回写（借鉴 Shadow）：插件命令可在返回值里挂 orbit.outbox，由 Plugin Host 统一消费 → 写 Inbox / 提 Proposal / 发 Activity。这样插件「在 Orbit 里运转起来」——例如 Habit 连续断卡时自动往 Inbox 推一张提醒卡。

09安全 / 权限 / 审批

UI 隔离

  • sandbox iframe + 自定义 protocol，无 Node、无 window.orbit
  • 所有调用经 Bridge postMessage，带 pluginKey 与 requestId（抄 ShadowBridge 的 launch-token 防伪）

能力授予

  • 安装时弹「权限清单」确认（manifest.capabilities）
  • 未授予能力 → 网关抛 capability_denied
  • data 写入硬锁 05_Plugins/<key>/ 前缀

审批接入

  • 复用 AuthorityRiskLevel + propose-approve
  • destructive tool → journal + Activity Log（既有 executor 自动做）
  • 高危能力 → 每次走 Inbox 审批卡

安装前扫描

  • 形态 C 后端代码 → 过 skill-safety-review 子代理静态扫描
  • 校验 manifest schema、目录穿越、外部网络声明

10生命周期与运行时

discover 扫描插件目录→ validate manifest+schema→ grant 权限确认→ activate 注册 tools/handlers/view→ run iframe+Bridge+Gateway→ deactivate 反注册

挂在 vault 生命周期上（openFsSession 时 pluginHost.attach(vaultPath)，关闭时 detach），与 CLI server / Auto-runner / Watcher 同级。plugin IPC namespace 暴露给 renderer 做安装/启停/列表 UI。

12需要你确认的边界问题

Q1 默认形态

是否同意以 形态 B（iframe UI + 声明式命令） 为默认，形态 C（子进程后端）作为高级选项？还是你的目标插件大多需要自定义后端逻辑（那应优先 C）？

Q2 数据落点

插件数据放 vault 内 05_Plugins/（随 Git 同步、跨设备）还是 .orbit/plugins/（不入 Git）？前者更"文件优先"，后者更像缓存。

Q3 命令执行

形态 B 的命令是否只允许「组合已有 Orbit 能力」（无任意代码），把任意逻辑全推给形态 C？这决定安全模型的严格度。

Q4 分发

插件来源：仅本地手动安装，还是要做一个插件市场/索引（类似 cloud-skill）？影响 P4 的设计。

一句话总结：Orbit 已经具备插件体系所需的全部底座（IPC 契约、Tool/CLI 双注册表、文件优先 Store 范式、surface profile 导航）。本方案只需新增一个 Plugin Host 粘合层 + 一份 orbit.app/1 manifest 契约，把这些底座按「Manifest 声明 → 翻译成一等 Tool/View/Store → 经 CapabilityGateway 收口」编织起来，即可让用户造的页面像 Kanban / Feed 一样在 Orbit 里真正运转。
